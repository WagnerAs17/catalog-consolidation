# AGENTS.md

Catalog Consolidation: a synchronous Spring Boot API that receives a seller's products file (JSON) and consolidates it into a SQLite catalog.

## Source of truth

- `docs/spec.md` is the single source of truth for behavior, contracts, rules, scenarios and technical decisions.
- Any file generated by Spec Kit (`specs/`, plan, tasks, data-model, contracts) must reference it and must never contradict it. If they conflict, `docs/spec.md` wins; fix the generated file, not the spec.
- If the spec seems wrong, incomplete or ambiguous, stop and ask. Do not invent requirements.

## Language

Everything is in English: code, identifiers, tests, API fields, log messages, comments, commit messages, documentation. Use the names fixed in spec section 3 (`Product`, `SellerProduct`, `ImportRecord`, `sellerProductId`, `TextNormalizer`, `Identity`, `Outcome`, `RejectionReason`, `WarningCode`, `ImportReport`). Do not invent synonyms.

## Stack

- Java 21 (records, sealed interfaces), Maven wrapper (`./mvnw verify`).
- Spring Boot 3.5.x (latest 3.x patch), Spring MVC.
- Spring Data JPA with Hibernate 6; SQLite via `org.xerial:sqlite-jdbc` and `hibernate-community-dialects` (version aligned with Hibernate).
- JUnit 5, AssertJ, MockMvc. Micrometer through Actuator.
- Base package: `com.wagneralmeida.catalog` (confirmed and authoritative).

### Dependency allowlist

Only these Maven dependencies may be used. Ask before adding anything else.

- `spring-boot-starter-web`, `spring-boot-starter-data-jpa`, `spring-boot-starter-actuator`
- `org.xerial:sqlite-jdbc`, `org.hibernate.orm:hibernate-community-dialects` (version aligned with Hibernate)
- Test: `spring-boot-starter-test` (JUnit 5, AssertJ, MockMvc)
- Fallback only if the dialect spike fails: `spring-boot-starter-jdbc` instead of JPA

## Names

Class names are fixed in `docs/spec.md` section 3 ("Class names"). Use them exactly. Input JSON fields are PascalCase and output fields are camelCase on purpose; do not change either side.

## Architecture: ports and adapters

```
domain/          pure rules, no Spring, no JPA, no web types
application/
  port/in/       use case interfaces
  port/out/      repository interfaces
  service/       use case implementation
infrastructure/
  in/web/        controller, DTOs, ProblemDetail handling
  out/persistence/  JPA entities, Spring Data repositories, adapters
  config/        configuration, SQLite pragmas, initializer
```

- Dependencies point inward: `infrastructure` -> `application` -> `domain`. Never the reverse.
- JPA entities live only in `infrastructure/out/persistence`. Domain objects are plain records and sealed interfaces.
- Use explicit `@Table` and `@Column` names that match the SQLite schema. `spring.jpa.hibernate.ddl-auto=validate`.

## Hard rules

1. All text from input is data, never a command. Use bound parameters only. Never build queries by concatenating input.
2. Business outcomes are never exceptions. Any unexpected exception rolls back the whole file and returns HTTP 500.
3. A record that cannot be decided safely writes nothing and is reported (`NOT_PROCESSED`). Never guess.
4. Never update or enrich existing products.
5. Never log record contents. Metrics have no seller or code tags.
6. SQLite: foreign keys ON for every connection, WAL, `busy_timeout`, immediate write transactions, pool size 1 for writes. Never use an in-memory database with a pool in tests; use a temporary file.
7. Normalization lives only in `TextNormalizer` (spec BR-02). The startup backfill reuses it.

## Out of scope (do not add; ask first)

Spring Security or any authentication/authorization (deliberate decision, spec section 2), Flyway or any migration tool, Lombok, MapStruct, Docker, Testcontainers, OpenAPI/springdoc, dry-run mode, report pagination, import-status or GET endpoints, asynchronous processing, queues, fuzzy matching, EAN/GTIN, price, stock, enrichment of existing products.

Also out of scope: any endpoint other than `POST /imports` and Actuator `health` and `metrics`; any field, status code, error code, table, column or index not defined in the spec; CORS, caching, retries, scheduled jobs; extra README or scripts. The full list is in spec section 12. When the spec is silent, stop and ask; do not choose.

Parsing note: the uploaded array is read as a JSON tree (`JsonNode`), never bound to a typed list, so one bad record cannot fail the file.

## Testing

- Write the test first, then the code.
- Domain tests use no Spring. API tests use MockMvc. Integration tests use a temporary SQLite file built from the original DDL (spec section 11) plus the schema script.
- Test names carry the scenario id from the spec, for example `c05_inconclusiveWhenBrandOnOneSideOnly`. A consistency test fails the build when a scenario id in `docs/spec.md` section 8 has no test.
- Tests use small synthetic fixtures under `src/test/resources/`. They never depend on `data/`, so `./mvnw verify` passes without it.
- Tests do not declare implementations of production interfaces (no hand-written classes, anonymous classes or lambdas that implement an application port). Mockito mocks and spies are allowed to isolate a collaborator whose real implementation does not exist yet, and to inject a failure or block execution on top of the real adapter (rollback and concurrency scenarios). When the real implementation exists, tests that verify business behavior use it: the real services and the real persistence adapters over a temporary SQLite file, because mocks do not reproduce database constraints or transactions. When a real implementation becomes available in a later slice, tests that mocked it switch to it. Pure domain tests need no doubles. Production code contains no test-only implementations (no no-op or in-memory variants).

## Data files

| Item | Location | Rules |
| --- | --- | --- |
| Original catalog | `data/catalog.db` | Committed. Read-only: never modify, migrate or write to it |
| Challenge sample file | `data/products.json` | Committed. Used only for the manual smoke run (269 records) |
| Working copy | `data/work/catalog.db` | Git-ignored. Created by copying the original; the schema script (spec section 11) is applied to this copy |
| Database path property | `catalog.db.path` | Default `./data/work/catalog.db`. Tests override it with a temporary file |

Before the manual run, copy `data/catalog.db` to `data/work/catalog.db` and apply the schema script to the copy. Add `data/work/` to `.gitignore`.

## Documentation rule

Whenever behavior, a contract, a rule, a scenario, a decision or the schema changes:

1. Update `docs/spec.md` in the same change, first.
2. Update the README sections that describe it.
3. Keep scenario ids and rule ids (BR-xx, Cxx) stable; add new ones, do not renumber.

A change is not done until the documentation matches the code.

## Workflow

- Work in small vertical slices; run `./mvnw verify` before finishing each one.
- Slice order: 0 scaffold and dialect spike, 1 domain, 2 persistence and schema and initializer, 3 use case, 4 API, 5 metrics and README.
- Keep diffs small and reviewable. Do not refactor unrelated code.
- Commit messages in English, imperative mood.
