# Catalog Consolidation

A synchronous Spring Boot API that receives a seller's products file (JSON) and consolidates it into a SQLite catalog.

- A product that is not in the catalog is created and linked to the seller.
- A product that already exists is **not** inserted again: only the seller link is created.
- A product the service cannot identify safely is **not written** and is reported.

`docs/spec.md` is the single source of truth for rules, contracts, scenarios and decisions. This README summarizes it.

## Run it

Requirements: Java 21. The Maven wrapper is included.

```bash
# 1. Working copy of the catalog (the original data/catalog.db is never modified)
mkdir -p data/work
cp data/catalog.db data/work/catalog.db
sqlite3 data/work/catalog.db < <path-to-schema-script>.sql

# 2. Start the API (reads ./data/work/catalog.db; override with --catalog.db.path=...)
./mvnw spring-boot:run

# 3. Send a file
curl -s -X POST http://localhost:8080/imports \
  -F "file=@data/products.json;type=application/json"
```

The schema script is applied by hand on purpose (see decisions). If it is missing, the application fails at startup.

Tests: `./mvnw clean verify`. They use temporary SQLite files and small synthetic fixtures, never `data/`.

## API in one screen

`POST /imports`, `multipart/form-data`, part `file` with a UTF-8 JSON array of objects (`Id`, `SellerName`, `Name`, `Brand`, `Category`).

It always answers **200** with a report when the file could be processed, even if some records are `NOT_PROCESSED`:

```json
{
  "importId": "6f1c0d52-0b8e-4c3a-9a57-2f0e4f7c1a10",
  "totals": { "records": 4, "createdAndLinked": 1, "linkedToExisting": 1, "alreadyLinked": 1, "notProcessed": 1 },
  "results": [
    { "position": 1, "sellerName": "Acme", "sellerProductId": "100", "outcome": "CREATED_AND_LINKED", "productId": 501, "warnings": [] }
  ]
}
```

File-level problems use `application/problem+json` with a `code`: 400 `FILE_UNREADABLE`, 409 `IMPORT_IN_PROGRESS`, 413 `FILE_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA_TYPE`, 422 `NOT_A_JSON_ARRAY`, 422 `TOO_MANY_RECORDS`, and 500 `INTERNAL_ERROR`. Limits (5 MB and 5000 records by default) are configurable with `catalog.import.max-body-size` and `catalog.import.max-records`.

Full contract: `docs/spec.md`, sections 4 and 7.

## How a record is decided

1. Validate the record. Invalid: `NOT_PROCESSED` / `INVALID_RECORD`.
2. Normalize name and brand, then look up the product by normalized name.
3. Decide identity: `Existing`, `New` or `Inconclusive` (brand present on one side only, or different brands).
4. `Inconclusive`: nothing is written, `NOT_PROCESSED` / `INCONCLUSIVE`.
5. Look up the seller listing `(SellerName, SellerProductId)`:
    - already points to the identified product: `ALREADY_LINKED`;
    - exists but the identity is `New` or another product: `NOT_PROCESSED` / `INCONSISTENT`;
    - does not exist and the product exists: `LINKED_TO_EXISTING`;
    - does not exist and the product is new: `CREATED_AND_LINKED`.
6. If the product existed and the categories differ, add the warning `CATEGORY_DIVERGENCE`.

Records are processed in file order inside **one transaction**. An unexpected failure rolls back the whole file (HTTP 500).

## Decisions and why

| Decision | Why | Trade-off accepted |
| --- | --- | --- |
| The seller code is not the product identity. A listing is `(SellerName, SellerProductId)` and points to one product | Codes are generated by each seller and only unique inside the seller. The sample file reuses 13 codes across different sellers for different products | Product identity depends on the name, so it needs the rules below |
| Identity = unique normalized name + compatible brand | The data has no EAN/GTIN. A unique index on `NormalizedName` makes the rule enforceable by the database, not only by code | Names are a weak identity; word order and synonyms are not handled |
| Brand on one side only, or different brands: `INCONCLUSIVE`, nothing written | Wrongly merging two products is silent and hard to undo; an unprocessed record is visible | Some legitimate records are left out and reported |
| Normalization: lowercase (`Locale.ROOT`), NFD without combining marks, drop quotes, non `[a-z0-9]` becomes a space, collapse and trim | "Câmera" and "Camera" must match (the sample has that pair). Numbers stay meaningful: `5.5` differs from `55` | Non-Latin names normalize to empty and are rejected |
| Existing products are never updated or enriched; a category difference is only a warning | Several sellers would fight over which data wins | A bad value already in the catalog stays |
| A listing is never redirected to another product | Keeps the seller history reliable; reusing a code for another product is `INCONSISTENT` | Correcting a wrong code needs a management flow that is out of scope |
| One transaction per file; business outcomes are never exceptions | All or nothing for system failures, while one bad record never blocks the others | A long transaction for big files, bounded by the 5,000 record limit |
| Synchronous API with an in-memory lock and HTTP 409 for a concurrent import | Bounded volume, SQLite has one writer. The lock does not protect integrity (the database already serializes writes); it makes concurrency fail fast and predictably instead of waiting and timing out | Valid for one instance. Production: asynchronous `202` + status lookup, queue, database with concurrent writes |
| Original schema changed by a script; no migration tool | `SellerProductId` was an integer but the codes are UUID strings, the unique seller+code rule was missing and `Product` needed `NormalizedName`. `SellerProduct` had no rows, so it is recreated. The startup backfill fills `NormalizedName` in one transaction, idempotent, and fails on a collision | Manual step. Production: versioned migrations in the pipeline |
| File read as a JSON tree, not a typed list | A malformed record cannot fail the whole file | Manual field-by-field validation |
| Ports and adapters, domain without Spring or JPA | Rules are tested without a database; persistence can change without touching them | More classes than a minimal version would need |
| No authentication or authorization | Deliberate scope decision to focus on the consolidation domain | Production needs both, with per-seller authorization |
| No fuzzy matching, no AI at runtime, no asynchronous processing | They contradict "never guess", remove determinism (expected totals would not be reproducible) and are outside the scope | Listed as future work |

## Out of scope (on purpose)

Authentication and authorization are deliberately out of scope, as are asynchronous processing and queues, fuzzy matching or AI-based matching, EAN/GTIN, updating or enriching existing products, endpoints other than `POST /imports` and Actuator `health`/`metrics`, report pagination, and dry-run mode. Full list: `docs/spec.md`, section 12.

## Testing

- Every business rule (BR-01..BR-11) and scenario (C1..C21) in `docs/spec.md` has a test; test names carry the scenario id, and a consistency test fails the build if one is missing.
- Domain tests use no Spring. Business behavior is tested against the real persistence adapters on a temporary SQLite file built from the original DDL plus the schema script.
- Mockito spies on real adapters are used only to inject a failure (rollback) or to hold an import (concurrency). Tests do not provide hand-written implementations of application ports.

## Observability

Micrometer metrics through Actuator (`catalog.import.records{outcome}`, `catalog.import.rejections{reason}`, `catalog.import.duration`, `catalog.import.failures`, `catalog.import.file.rejections{code}`). Record counters are updated only after the commit. Logs carry an `importId` and never include record contents.

## How AI was used

<!-- Adjust to what really happened; keep it factual. -->

- The work was spec-driven (GitHub Spec Kit): constitution, specification, plan, tasks, analysis, then implementation one slice at a time, always test first.
- `docs/spec.md` is the source of truth. `AGENTS.md` fixes names, allowed dependencies and out-of-scope items so an agent cannot invent scope.
- Rules were checked against the real catalog and sample file before implementation (975 products, no normalized-name collisions; expected totals computed independently).
- Generated artifacts were reviewed, not accepted as is. Examples of what had to be corrected: contradictions between generated documents, requirements that were not in the spec, a JDBC fallback plan that could not be executed, an unverified framework patch version, and an edge case in empty-file handling.
- Decisions I kept or rejected after questioning the proposals: the synchronous design with a lock, brand handling, no AI at runtime, no Chain of Responsibility in the controller.

## Future work

- Asynchronous import: `202` with the `importId`, status lookup, a queue and a database with concurrent writes.
- Matching by EAN/GTIN; AI only as a suggestion for `INCONCLUSIVE` records, with human approval.
- Seller-managed listings (update or remove a link), audit trail and authentication with per-seller authorization.
- Versioned database migrations and distributed tracing with a correlation id accepted from the caller.
